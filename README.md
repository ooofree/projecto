# Project O — 项目管理平台专业重构

> 目标：从零构建一个轻量、可即开即用、以插件扩展的建筑项目管理平台。功能覆盖现有系统，业务规则、计算结果、权限边界和流程语义保持不变。

本目录本身就是独立的新项目根目录，包含架构规范和新实现代码。旧系统 `m` 仅作为业务行为参考；在明确批准数据迁移和切换前，不覆盖、不删除、不修改旧系统代码或数据。

## 当前开发状态

新项目已实现最小 PHP/MySQL 运行骨架、首次管理员初始化、登录/退出、基础权限、插件清单发现/路由注册，以及 `project.foundation` 插件中的项目和楼栋/楼层/区域/房间管理。项目和空间支持受保护删除：无关联时删除，有关联时归档并可从回收站恢复。平台后台支持系统主题、默认国家/币种、用户与角色权限管理、插件启停和安全运行参数展示；管理权限由 `manage_platform` 授权，停用账号保留数据，必需/有依赖的插件不能停用。货币代码从 ISO 4217 标准目录选择，默认币种为人民币 CNY；选择币种不自动换算或改写已有金额。`document.management` 首期提供项目内问题与 RFI 管理、列表与模态编辑、独立状态流转、关闭校验、后续事项和状态审计；问题/RFI 不提供硬删除。`material.management` 的材料分类、材料、辅材、估算、样品、报价和招标清单按当前项目隔离；供应商、供应商材料和品牌为共享目录。样品图片使用可选的私有对象存储适配器。招标清单按项目而非楼栋维护材料、数量、单价和币种；项目基准币种为 CNY，招标项默认 CNY，也可选择其他 ISO 4217 币种。全站页面共用现代化响应式视觉组件，覆盖项目、空间、材料、文档、后台及登录界面。**现有全局材料/分类/辅材/报价记录不会由迁移自动分配到项目；需核实所有权后另行制定数据归属迁移。** 目标设计见 [ARCHITECTURE.md](ARCHITECTURE.md) 和 [FEATURES.md](FEATURES.md)。采购、库存、BOM、成本公式、图纸/传递、文档附件及项目成员权限仍待后续开发。目标数据库必须是新建的空数据库，与旧系统数据库隔离；当前不导入或更改旧系统数据。

安装器只负责创建首位管理员；其后可在后台创建/停用用户并配置角色权限，但尚未实现项目成员分配。项目列表权限由角色权限控制。项目级成员隔离必须在核实旧系统实际授权规则后实现，当前版本不能据此宣称支持多租户隔离。

完成后可按下列步骤启动（需 PHP 8.2+、mbstring、PDO MySQL、Composer 和 MySQL）：

1. 在 MySQL 中创建专用空数据库和仅供新项目使用的账号，例如：
   ```sql
   CREATE DATABASE project_o CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   CREATE USER 'project_o'@'localhost' IDENTIFIED BY 'replace-with-a-unique-secret';
   GRANT ALL PRIVILEGES ON project_o.* TO 'project_o'@'localhost';
   ```
   请替换示例密码，并按部署环境调整 MySQL 主机/账号。
2. 复制 `.env.example` 为 `.env`，配置 `APP_DSN`、`APP_DB_USER` 和 `APP_DB_PASSWORD`。
3. 运行 `composer install`。
4. 运行 `php bin/install.php`；首次安装会交互式创建管理员，密码至少 12 个字符。
5. 运行 `php -S 127.0.0.1:8000 -t public` 并打开 `http://127.0.0.1:8000`。

不要把 `.env`、真实密码或生产密钥提交到版本库。安装器拒绝对非空数据库首次建表；请勿把旧系统数据库用作新项目的安装目标。

### 样品图片存储（可选）

启用 R2 图片存储时，除上述依赖外执行 `composer require aws/aws-sdk-php`，并在 `.env` 中配置 `APP_OBJECT_STORAGE_ADAPTER=ProjectO\Modules\MaterialManagement\R2SampleImageStorage`、`APP_R2_ACCOUNT_ID`、`APP_R2_BUCKET`、`APP_R2_ACCESS_KEY_ID` 和 `APP_R2_SECRET_ACCESS_KEY`。R2 bucket 应保持私有；应用仅生成 5 分钟有效的读取签名 URL。上传限制为 PNG/JPEG/GIF/BMP/WebP、单文件 5 MiB；PHP 部署的 `upload_max_filesize` 和 `post_max_size` 也应允许至少 5 MiB 请求。未配置适配器、凭据或 AWS SDK 时，样品跟踪可继续使用，但图片上传/查看明确不可用。

测试：运行 `composer test`，覆盖认证、项目插件/服务、材料/空间/样品服务、文档问题/RFI 服务、后台设置/权限/插件启停和页面授权。迁移与服务行为测试使用 SQLite 等价结构；部署前应在专用测试 MySQL 验证迁移，不得直接对生产库执行未审阅迁移。

插件清单声明的迁移会在运行 `php bin/install.php` 时由核心迁移追踪器执行；插件停用不会删除已创建的数据表或记录。

## 不可妥协的约束

- **业务等价优先**：重构代码和存储方式可以变化，业务规则及其可观察结果不能自行改变。
- **项目是业务根上下文**：先创建或选择项目，再开展该项目下的文档、图纸、RFI 和其他业务；项目归属与访问范围必须遵守旧系统的真实规则。
- **插件化但不拆服务**：采用模块化单体；插件在同一应用进程内运行，不引入微服务及其运维成本。
- **核心小而完整**：启动、配置、身份认证、权限、数据库访问/迁移、路由、插件注册、日志与错误处理属于平台核心；具体业务属于插件。
- **按需启用**：可选业务模块可安装、启用、停用；基础认证、项目上下文、数据库及插件管理等运行必需能力不得被误停。
- **渐进迁移**：每个模块均可独立实现、验证和交付；旧系统保持可用，直到新旧行为对照通过并完成有计划的切换。
- **即开即用**：新部署有明确、短路径的安装和首位管理员配置流程；不得把默认账号密码、生产凭据或危险的自动建库权限写入代码。

## 项目现状与技术基线

旧系统是 PHP 服务端渲染应用，`composer.json` 要求 PHP 8.2+，数据库逻辑使用 MySQL 表、视图、触发器和存储过程；现有依赖包含 PhpSpreadsheet、Dompdf 和 AWS SDK。它同时有传统 PHP 页面和 API。新项目可重新组织代码，但必须先审计实际在用的规则与数据，再决定如何封装或替换这些依赖。

本规范只定义目标和护栏，不预先假定所有遗留页面、迁移脚本、注释和数据库定义彼此完全一致。开发前应以正在运行的行为、有效数据库定义、样例数据和用户确认的流程为准，记录并解决差异。

## 推荐交付顺序

1. 盘点遗留行为、权限、数据关系及数据库自动化，建立基线。
2. 创建新项目骨架和最小核心，提供安装向导及一个可验证的示例插件。
3. 先完成身份/权限与项目基础数据；所有项目业务插件都依赖项目上下文，再按 [功能基线](FEATURES.md) 的依赖顺序迁入。
4. 每个插件通过行为对照、权限检查、迁移检查和回归验收后，才进入试运行。
5. 备份、校验、演练回滚并获得明确批准后，再安排生产切换。
